## 谷歌相册规则不生效

实机规则已经包含 `com.google.android.apps.photos`，但过滤目录名开头多了 `U+2009 THIN SPACE`。配置路径不存在，真实目录不带这个字符。按字面路径匹配时，两者是不同目录。

通过原模块的 Binder 接口仅修正这一处路径，并校验完整 JSON，确认应用绑定和其他规则字段未改变。该模板被多个应用共用，路径修正对所有已绑定应用生效。没有修改媒体文件，也没有清除谷歌相册数据。

验证使用临时 Java 探针：root 获取 MediaProvider 句柄，随后将进程 UID 降到谷歌相册的实际 UID，使用其包名归属信息执行查询，仅输出行数。调用的是系统 MediaProvider 和现有模块，不是 SQL 模拟。探针检查 files、images、video 三个集合。

| 查询范围 | 修正前 | 修正后 |
| --- | ---: | ---: |
| 目标目录 images/media | 2,096 | 0 |
| 目标目录 video/media | 41 | 0 |
| 目标目录 file | 2,137 | 0 |
| DCIM images/media 对照 | 4,722 | 4,722 |
| DCIM video/media 对照 | 224 | 224 |
| DCIM file 对照 | 4,946 | 4,946 |

这证明该设备上谷歌相册身份的 MediaStore 查询过滤有效。该验证不代表谷歌相册已删除自己的历史索引、缩略图或云端副本；模块也不是文件系统访问隔离工具。

- 用显式保存替代输入期间的自动写入，返回时提示未保存更改，保存失败保留草稿并提示。

- 返回按钮的防重复点击改为短时间节流，避免取消退出对话框后返回按钮永久失效。

## 后续值得改进

1. **规则诊断**：由 MediaProvider 侧检查目录存在性、匹配媒体数量及当前绑定，避免受管理应用自身存储权限影响而误报路径不存在。
2. **拦截降级可见性**：SQL 过滤被系统拒绝时目前会放行并写日志，管理界面应显示降级状态，不能只依靠“模块已激活”。
3. **记录定位**：应用详情直接打开该应用的使用记录；将最近是否拦截与累计调用次数分开显示。
4. **其他写操作反馈**：模板绑定、删除、设置和恢复仍使用旧的写入流程，应统一接入可报告失败、避免过期快照覆盖的更新接口。
